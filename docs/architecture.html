Tugboat architecture

Tugboat connects a local project folder to Codex and Claude Code on an Apple silicon Mac. Each agent runs in its own Brig guest. Both can edit the same project files.

What belongs to whom

One project can have a Codex environment and a Claude Code environment. One environment can have several chats. A live terminal has a shorter lifetime than either a chat or its environment.

Desktop commands and events

Tauri 2 hosts a local web interface and a Rust process. Vite builds the TypeScript and page assets. The web interface uses the document object model and Zustand stores for the active project, account summaries, terminal lists and dashboard state.

On startup, Rust resolves the records location and starts usage storage on a background thread. It creates a hidden window and starts monitors. The interface calls frontend_ready to show and focus the window. Controllers then load records, settings, account status and projects. A storage failure remains visible through the recovery controls.

The web interface calls named Rust commands through Tauri interprocess communication (IPC). Rust owns process creation, the registry, account credentials and writes to disk. It validates inputs at the command boundary. The main window restricts navigation to the app origin, with a loopback development origin, and denies new windows. Browser authorization runs outside it.

Commands return snapshots. Events can arrive before the command that requested an older snapshot finishes. The dashboard checks project ID, request revision and event sequence before applying a result. If a refresh fails, it can display saved data with an error. A project switch invalidates the old request.

From New Chat to a guest process

  1. Resolve the selection. The interface sends the project and environment identifiers. Rust reads the registry, checks the folder identity, and resolves effective settings for the selected agent.
  2. Prepare the binding. Preparation looks for a Brig session that matches the folder and agent. It can create a binding, adopt one matching session, or return candidates for a user choice. A detached policy or an incomplete removal needs its own recovery path.
  3. Check the execution plan. Rust reads the profile, policy, plan and inventory. It verifies the host folder, guest project path, home, and protected records directories. A fingerprint identifies the reviewed configuration. A changed fingerprint requires another review.
  4. Verify the guest. The app reuses a matching running environment or starts one. Preparation associates its terminal with an attempt. A late result must match the current attempt. A successful command exit still requires evidence from the guest.
  5. Admit the chat. Session code checks the environment, online mode, provider account, and required guest capabilities. Resume also checks the saved session. A matching live chat can return its existing terminal identifier.
  6. Run the command. The agent module builds an argument list. Rust starts the selected Brig executable through a PTY. Codex assigns its own new chat ID. Tugboat supplies a new UUID (universally unique identifier) for Claude Code. Resume uses the existing native ID.

For example, a user can switch to Claude while Codex preparation is running. The selected agent can change immediately, but the outstanding Codex result still belongs to the Codex environment. Independent environment identities and attempt checks keep that result from enabling a Claude chat.

Terminal input and output

The web interface reserves the terminal area and sends layout and focus requests. Rust attaches an AppKit view to the macOS window. The native view uses libghostty-vt to interpret terminal data. Keyboard input, text composition, selection and drawing use the native surface.

Rust gives each child process a controlling PTY. Incoming keystrokes enter a bounded queue so native input callbacks can return promptly. A full queue raises a terminal input error. The reader forwards child output to the native surface. A resize updates the PTY size so the child can redraw.

A local terminal starts a shell on the Mac in the project folder. Guest shells, agent chats, and guest Git or test operations go through Brig. Diagnostic actions such as Brig info and logs invoke the host CLI for the selected reference. A terminal view alone does not establish where a command ran.

The terminal registry admits up to 16 live processes and retains up to 32 finished views during one app session. Closing an output view releases scrollback. New Chat creates another conversation. Selecting a live chat restores its own surface and process.

Accounts and access boundaries

Provider sign-in belongs to application Settings. ChatGPT uses a browser device code. Claude uses a temporary loopback callback and proof key for code exchange (PKCE). The Rust login worker owns the attempt, checks the provider response and saves the result. A cancelled attempt cannot publish a late result.

Tugboat keeps renewable sessions in private files beneath the verified records directory. A compatible Codex guest receives an access copy in the standard guest credential location. Managed Claude environments receive an access copy in memory. The Claude helper preserves other connector credentials. Only the private host records contain the shared refresh tokens.

The project share is writable. Private records stay outside directories exposed by the guest plan. Brig and hull apply the guest network policy. Offline mode blocks guest network access. Mac browser sign-in and provider-hosted tools have different network paths. A hosted search result cannot establish that a guest command reached the same host.

Codex normally uses the Brig boundary with its inner sandbox disabled. The optional workspace sandbox restricts writes and command network access. Codex approval remains never in either mode. Claude Code runs in manual permission mode. The selected profile and network policy still apply in both cases.

From transcript to usage

Command output is transient. History readers use agent-owned files under verified guest homes. Codex rollouts and Claude transcripts have different formats and identity rules. The app can inspect persistent history while the guest is stopped.

  1. Read sourcesCheck the guest home, project membership and source cursor.
  2. Resolve identityMatch requests and verify parent links within the source namespace.
  3. Commit factsSave changed usage and parser progress in one SQLite transaction.
  4. Project totalsRead saved summaries for a dashboard or load a selected family's details.

The history monitor checks observed environments about every two seconds. A parser cursor records the source position so an append can resume. Restarting a scan must preserve previous measurements and avoid counting the same physical request twice. SQLite keeps usage, source references, summaries, prices and corrections. Full message bodies remain in the agent files.

Codex can use the guest namespace, provider, origin thread ID and response ID as physical request identity. Claude uses stable message IDs and verifies parent evidence for child transcripts. Ordinary forks remain distinct roots. Unresolved relationships appear as read-only unlinked subagents. Aggregate views include verified descendants once.

Cost is an API equivalent based on the persisted token counts and dated rates. Unknown counts, missing prices and measured zero have different meanings. Historical prices and corrections stay attached to their requests. Claude coverage remains partial even when every discovered message has counts.

Durable records and recovery

The default records folder is ~/Library/Application Support/Tugboat. A small location pointer and lock in the default directory identify the active records folder. The directory marker identifies the dataset. The database records the same identity.

Data locations and recovery rules
LocationContentsRecovery rule
Active records folderProject registry, settings, interface preferences, managed profiles, diagnostic records, and private provider files.Use the verified records location. File publication checks ownership and syncs the temporary record before replacement.
usage.sqlite3One database holds both agents' usage across projects, chat state, request facts, source cursors, saved prices and derived summaries.After activation, SQLite is authoritative. A missing or damaged active database blocks usage writes. Preserve the database and any rollback journal.
Retained JSON ledgers and backupsEarlier usage records and migration evidence. The first SQLite activation verifies the import before publication.Retain the original inputs. They can predate newer SQL writes. A legacy writer can lose post-migration work.
Guest homes and project folderAgent-owned transcripts, persistent guest files, and the user's source tree.A records move transfers Tugboat records. Brig continues to own its homes and the project keeps its original location.

A records move begins as a pending operation. On a successful shutdown, writers stop, usage is flushed, and the database closes. Startup copies and verifies the dataset before committing the location pointer and cleaning the source. Locate can reconnect the same dataset at a different path. An incomplete copy cannot become the active dataset.

After an uncertain commit, the next access must reopen the verified database and establish its state before scanning again. A disconnected drive can look like an empty directory. Preserving the saved identity lets recovery distinguish those cases.

Stop, remove, and quit

Stop an environment. The operation takes an environment-scoped gate and targets that guest's processes. The other agent can keep working. Stopping preserves the registered project and persistent history.

Forget an unavailable project. Once its project terminals have ended, the user can forget the library entry. Tugboat removes the registration and stops watching it. It preserves project files, Brig environments, guest homes, and recorded usage. A later registration can receive a different project ID.

Remove an environment. A preview identifies the reference, guest home and policy. The user confirms that scope. Native code checks the target again and records completed steps. It preserves a replaced target or a policy that it cannot prove it owns. An interrupted removal resumes from the recorded step.

Quit or restart. The desktop lifecycle asks for confirmation when a terminal process is active. On confirmation it drains terminal processes, waits for host commands, flushes provider work and usage, then closes storage. A failure prevents completion and returns an error. A project switch has none of these shutdown effects.

Build and distribution

The native target is Apple silicon with macOS 15 or later. Tauri bundles the web assets, native terminal code, fonts and host runtime. The build prepares pinned inputs for Ghostty, Brig, hull, the signed virtualization runners, verification tools and ext4 disk utilities. The bundled registry configuration supports public guest images.

An empty Brig CLI setting selects bundled Brig. An explicitly saved compatible path selects a custom Brig CLI. Runtime validation checks the supported version, required tools, configuration and hashes against the bundle manifest. A system report identifies the effective tool paths.

Pull requests run web checks and select additional macOS tests for native changes. The trunk workflow builds and publishes an ad hoc signed installer. A separate Developer ID release script signs and notarizes the app and disk image with Apple credentials. Packaging success and end-user Gatekeeper acceptance require different evidence.
