Set up a checkout

The native target is Apple silicon with macOS 15 or later. Install Xcode and its command line tools, Rust with Cargo, and Node.js with npm. Use the recorded versions in config/development-versions.json to reproduce a build. The supported Node.js ranges are in package.json. Keep the npm and Cargo lockfiles with changes to their manifests.

From the repository root, install the locked web dependencies and build the interface. The build checks TypeScript before Vite writes the web assets into dist/.

npm ci
npm run build

For interface work, npm run dev serves Vite on 127.0.0.1:1420. The fixture harness supplies native commands and events to interface tests. For desktop development, npm run tauri -- dev prepares the native runtime and starts Tugboat Dev from the checkout.

The window title and the About menu item identify Tugboat Dev. Tauri uses the identifier sh.brig.desktop.dev. The command runs the tugboat executable from the Cargo build folder. It saves settings, project records, provider sign-ins, and usage in ~/Library/Application Support/Tugboat Dev by default. This folder has its own location pointer and lock.

Development Brig commands use ~/.tugboat-dev as their home. A local terminal uses your usual home. If you select the same project in both apps, both can edit its source files.

The first native preparation can download and build pinned dependencies. Tauri's standard hooks use the default preparation mode, which can sign local helpers. The pull-request workflow uses a separate mode for native tests. Use the commands in Choose checks when testing under a signing restriction.

Ghostty preparation downloads the library, dependencies, and Zig archives with up to two retries for transient failures. Each attempt has a 15-second connection timeout and a 180-second transfer limit. Downloads use a temporary .partial file. Preparation checks the pinned SHA-256 digest before caching and extracting an archive. A checksum failure stops preparation. For a cached archive mismatch, remove only the named archive under .build/libghostty, then retry preparation.

Interface and command contracts

The window contains static HTML and TypeScript controllers. src/main.ts wires selection, preparation, accounts, history, and terminal navigation. For a feature with an existing controller, put behavior beside that controller. Keep the entry point responsible for passing its context and callbacks. The shared Zustand store in app-data.ts holds the selected project, accounts, terminal lists, and other display values.

At an asynchronous boundary, capture the project and environment before starting work. Use sameProject to check the identifier, environment, and project epoch when the result arrives. Use sameProjectView for a result that belongs to one opening of Project Settings. A revision from RequestState distinguishes an older request for the same screen. A late response can otherwise put the first project's policy text in the second project's editor.

Use the controller's existing state transitions. For forms, FormState retains loaded values after a failed save and invalidates pending work on reset. For dialogs, showDialog manages the active modal and restores keyboard focus. The sidebar queues preference writes so a slow restore cannot undo a recent resize. Render titles, paths, and diagnostic text with textContent. Keep control labels and keyboard behavior consistent with the design guide.

Check a changed dialog in the native app. Verify its name and controls with VoiceOver. Check forward and reverse Tab, Escape, and focus after close. Repeat with a second dialog open. A frontend fixture cannot verify the native accessibility tree.

Project settings uses a named section with a dialog role inside the workspace. Use dialogOpen to check its state. The dialog controller makes the background inert, confines keyboard focus, and restores the opening control. Usage, removal, and record dialogs use native HTML dialogs.

Change a native command

Tauri carries inter-process communication between the web view and Rust. The interface calls invoke with a command name and named arguments. Rust registers commands in tauri::generate_handler!. Extend an existing command when the new action fits its contract. For a new command, implement the handler in the owning module and register it in the entry point.

The command registrations serve the bundled interface. Use the shared provider controls for sign-in. Pass the project ID, environment ID, and agentKind to start_agent_session, conversation_usage, and change_conversation_state. Use the native sessionId for saved-chat actions. The dispatcher checks the agent before it calls the native adapter. Usage details include the agent kind so the interface can verify the reply.

Decode external values into the appropriate Rust type, then resolve ownership from native records. Preserve the established camelCase fields and serialized enum values. Keep time-consuming file and process work off the window thread with the existing blocking-task pattern. Return the result needed by the controller. A TypeScript annotation on invoke<T> describes the expected response. The Rust handler still has to validate incoming identifiers, arguments, and target state.

For an event, inspect the emitter and the listener together. A terminal-exit event identifies a terminal and its project. Dashboard updates carry a sequence. Use those fields to ignore a late update and reconcile with a snapshot after a subscription or view change. Exercise the sequence with delayed promises in the interface harness. Keep the window permission set limited to the operations the UI needs.

Desktop lifecycle and settings

Rust resolves the records location before it starts the usage worker. It then creates the window. The web view invokes frontend_ready to show and focus it. Starting the worker and completing database activation are distinct events. Code that needs usage records obtains the verified store from the runtime. Keep unrelated interface startup work independent of a slow project reset.

For a new menu action, add the native item and its action identifier in desktop/menu.rs. Wire the corresponding menu-action listener in TypeScript. Update update_menu_state when availability depends on a selection or process. Expose the same behavior through an accessible control where the product design calls for one. Check keyboard activation in each applicable view.

Quit, window close, and a records move that needs a restart share the shutdown path. The AppKit delegate defers a macOS quit request until the lifecycle reports success or cancellation. The lifecycle cancels provider login, drains terminal processes, and waits for host commands and project operations. It flushes provider work and records final usage. The shutdown worker then stops registered guests through the bundled Brig and verifies the result before closing the database. Simulate a failed stop and a failed final write. Both must allow recovery and retry.

Choose the scope of a preference

Application defaults live in settings.json. Tugboat combines the Codex and Claude host lists when it creates a project policy. The shared record owns the effective CPU, memory, image pin, network mode, and policy binding. The bundled Brig runtime assigns one isolated /30 network per guest. It uses 198.18.2.0/24 after the 64 slots in 198.18.1.0/24 fill. Existing slots keep their addresses. Signature verification is required. The save path checks the selected physical guest before changing its settings.

For an execution preference, follow its value from the form to native validation, persisted settings, effective project settings, and the checked plan. For an interface preference such as sidebar width, follow interface.json and the preference save queue. Add a decoding fixture for an existing installation. Check missing fields, invalid values, and how defaults apply when a project already has an override. The settings save command writes the chosen settings before it attempts to apply Brig telemetry. Preserve its separate report of the recorded Brig state.

Projects, policies, and preparation

Project registry schema 3 gives a ProjectRecord one folder identity and one shared environment. EnvironmentId::for_project derives its ID. The record requires the managed profile and reserved label. Registry::agent_environment supplies a transient agent view for chat commands.

Registration checks the selected folder and its write access. Folder identity includes filesystem evidence such as inode and volume identity. A different folder can later occupy the same path. The library checks registered folders on entry, on window focus, and periodically while visible. Availability checks preserve the registry entry for a missing volume. When changing the rescan, test an available folder becoming unavailable, the original volume returning, and a replacement at the same name. Verify recent ordering and keyboard focus survive a background refresh.

Trace a setup failure

  1. Resolve the project environment. First-chat setup starts automatically when the host check succeeds and the selected provider connects. prepare_project checks the managed profile and the reserved reference. It creates or rechecks the project policy. The live guest must match the recorded project mount, guest home, and image digest.
  2. Read the plan. checked_environment resolves the environment from the registry. It checks folder identity, setup stage, current policy, profile, Brig plan, and the separation of private records from exported shares. The interface receives a fingerprint for these settings.
  3. Start the guest. prepare_environment uses the current checked fingerprint. It records the attempt token and terminal identifier. The operation gate rejects conflicting work for the same environment.
  4. Complete the matching attempt. Completion checks the current attempt, running guest, both agent executables, and plan. A late result cannot mark a different attempt ready.

The frontend keeps one pending New Chat request for the selected project, environment, and agent. It launches the agent after native verification and provider account setup. Cancellation, failure, or a project or agent change clears the request. A failed attempt retains its terminal output.

A successful startup command emits environment-preparation-verifying with projectId, environmentId, and terminalIdentifier. cancel_environment_preparation validates the same identifiers and stops the running process. A process in final verification cannot be cancelled. A cancelled attempt preserves the guest home and uses the existing retry path.

When changing a stage, check its serialized spelling in Rust and TypeScript. Follow its uses in preview, prepare, launch, and removal. A new intermediate stage needs a defined response to restart or retry. Check a changed plan between preview and launch, a terminal that exits before the interface reads its snapshot, and an older exit after retry.

Maintain a policy or boundary check

Policy document ownership and binding ownership are separate. A document can be external or shared, even if Tugboat owns the binding. Route save, accept, attach, and detach through the policy state and editor. Recheck the current document before writing. Invalidate preparation after an edit. Exercise an external binding and a competing edit with the old fingerprint.

The boundary report records the environment and the fingerprint used for its probes. The probes check the guest kernel, writable share, outside-file visibility, and network behavior. Keep the outcomes pass, fail, and inconclusive distinct. Preserve files whose ownership changed during a probe. A changed plan, failed cleanup, or unreachable comparison destination affects what the result can establish. A boundary report is diagnostic evidence for that run.

Project operations and removal

Operation owns the set of Git, test, and diagnostic actions. Its needs_guest decision determines whether the operation needs a verified running guest and a current plan fingerprint. Git and project tests run in the selected guest. Doctor, info, policy checks, and logs call Brig on the Mac for the selected target. For the test button, native code detects a supported manifest and chooses a fixed command. The user's repository still determines what its test script executes.

For a new action, choose its execution location first. Build an argument vector with the existing Brig adapter. A fixed shell fragment inside the guest can use its project environment variable. Keep path or label values out of generated shell text. Name the terminal purpose so the sidebar and stop logic can identify the process. The worked Git example covers the full route.

Stop verifies the Brig reference and ends the project’s guest processes. Forget removes the registration of an unavailable project. Removal checks the fingerprint and confirmation text against the current preview. Include both agents’ affected terminals in its scope.

For cleanup changes, inspect Removal::next_step. Match each saved step with its observed external effect on retry. Exercise a changed preview, an interrupted step, and a sibling project. Check that each path preserves project files and external resources.

Review and update a project image

The image update command checks the project, environment, and bundled Hull recovery build. Read distinguishes the recorded pin from a current Hull instance that already uses the candidate. Review checks the previous instance and verifies the signed candidate before stopping the idle guest.

Image review and terminal launch use the same project environment lock. A local terminal holds the lock until launch publishes its session. Review refuses active chats and terminals before saving its recovery state.

Review captures the writable system disk and lists its changed paths. Apply requires its saved review token. Verify the candidate’s running digest and both executables before committing the new pin. Keep current restores the reviewed system disk. The saved state allows the project to resume recovery after restart.

If inventory fails, keep Apply unavailable. Preserve the saved recovery state and show the runtime error. Exercise both the restarted recovery and a separate project that remains on its recorded image.

Brig, hull, and the host runtime

Brig manages sandbox sessions. The packaged runtime uses hull with the hvi backend. platform/runtime resolves the runtime directory and checks the manifest and file digests. Host inspection reports the effective tools. An empty Brig CLI path selects the bundled executable. A user-specified Brig path still needs a compatible version. Keep the package manifest and runtime resolution in step when changing a helper.

Hull checks the executable path and arguments of the guest process on macOS. An app name or project path can contain spaces. Test both agents from such a bundle. Before stopping an isolated environment, record the process IDs for hvi and its hull network-gateway. Verify that both processes exit and that a running sibling still answers.

Use platform/command.rs for bounded host subprocesses. It clears the inherited environment, installs an explicit set of variables, and tracks cancellation, timeout, exit status, and excess output. The Brig environment supplies the bundled helper paths and a private registry configuration for public images. Inspect the result status before parsing output. When reading Brig JSON, check the API version, result kind, and required data through the existing adapter.

The Brig plan check verifies the profile, session, writable share, limits, network posture, image verification, and bound policy. It rejects forwarded host credentials, host skills, and published ports. Extending the plan affects both plan validation and what the user can review. Add ready and refused fixtures with the same schema version. Check an otherwise successful response with an invalid field. A successful process exit alone says nothing about the target or the shape of the payload.

Use the shared project guest proof to check both supported programs in one disposable Brig guest.

Native terminal

A pseudo-terminal (PTY) connects an interactive process to the terminal view. Rust opens the PTY and manages process groups, input, resize, output, and exit. A macOS AppKit view uses the Ghostty terminal library to interpret bytes and draw cells. TypeScript supplies the visible rectangle and focus. For a text composition issue, begin in TerminalInput.m. For a missing glyph, inspect TerminalDrawing.m and the font setup. For an orphaned process after close, begin in terminal/pty.rs.

Route wheel input through Ghostty's current mouse protocol when an application requests mouse reporting. Encode wheel presses with pointer coordinates and modifiers. Use the same terminal pixel scale for resize and mouse input, with at least two pixels per point to preserve half-point cells on 1× displays. Send these bytes directly to the PTY so scrolling does not trigger the keyboard path's return to the bottom. Without mouse reporting, alternate-screen cursor scrolling requires DEC mode 1007. Normal output uses terminal scrollback. Keep precise fractional motion and normalize slow discrete macOS wheel ticks.

A native view and a guest process have distinct lifetimes. Terminal startup reserves an identifier before it attaches the view and spawns the child. Closing the reservation blocks a late attachment. The process manager shares a start/stop gate for the equivalent race at process creation. Deliver native view work on the main thread. Preserve the bounded input queue and the output reader's acknowledgement when changing throughput.

Environment startup opens its terminal in the workspace. EnvironmentBoot tracks startup, verification, cancellation, and completion for the project, environment, and terminal. A new native setup view stays hidden until its identifier returns to the matching selection. Navigation hides the presentation while the process continues. After success, the interface closes the finished setup terminal. If preparation fails after the terminal starts, the output stays available for diagnostics. Show the error and retry action on every failure.

Preparation result events arrive before the process leaves its finishing state. Before automatic closure through terminal_close, check the terminal snapshot and wait until running is false. Match the project, environment, purpose, and terminal identifier. Keep the terminal available when the exit or preparation result reports a failure. After a launch ends, check completed setup terminals across cached projects so early success and reused terminals follow the same rule.

The native terminal sits above the webview. The optional Layout.overlay rectangle reserves the centered HTML card in terminal-surface coordinates. Rust validates the rectangle. AppKit clips drawing and input to reveal the card below. Omit the rectangle to restore the full terminal. Dialogs still hide the native view.

boot-animation.ts uses bundled Three.js without external textures. It shows a still scene for reduced motion and releases its renderer, geometry, materials, frame loop, and listeners when hidden. Keep status text available if WebGL cannot start. Test late startup responses, environment switches, modal focus, and selection of a running local terminal.

Conversation history and dashboards

The conversations module reads agent-owned files from the checked environment. Codex rollouts and Claude transcripts use different formats. Each adapter produces source evidence about the session, guest namespace, project path, parent, availability, and usage. A native identifier can recur in another guest. Keep each observation scoped to the project and environment through the store, event, and interface cache.

Brig derives the guest project path from the folder name. When the registry verifies and relinks the original folder, it records the former guest folder name. History and resume checks recognize that name within the checked environment. New commands use the current execution plan.

The history graph resolves root and descendant relationships. A normal fork remains a separate chat. A recognized subagent contributes to its root's family total. Missing, inconsistent, or unsupported relationship evidence has an explicit status. Preserve the session's own measured usage in that case. A root chat action checks its family for running processes. Archive, delete, and restore change the saved display state and preserve the native transcript and recorded project total.

There are three read paths for the project dashboard. saved_project_dashboard loads saved usage before a guest check. recorded_project_dashboard refreshes from SQLite and can keep availability that an earlier live observation verified. project_dashboard checks environments and synchronizes source history. The monitor sends project-usage-updated for changed observations. In the interface, DashboardState orders events and requests and retains usable data on a failed refresh.

For a new row field, decide whether its source is a verified observation or a saved fact. Define its display when the volume or guest is unavailable. Propagate it through the summary, detail query, and frontend types only where the feature requires it. A detail cache uses project, environment, and session identity, plus a revision to detect changed content. Test an old snapshot arriving after a new event and two guests with the same native session ID.

Usage parsing and prices

Codex parsing tracks a cursor for each rollout source. The cursor records the file identity, header fingerprint, byte offset, and reconciliation state needed to resume counting. An incomplete last line can receive more bytes later. Replacing or truncating the file can require a replay. Match an exact request to its source and previous observations before increasing a count. Store progress with the facts it explains.

Claude usage comes from assistant messages in main and subagent transcripts. Repeated stream entries can refer to one response. The reader uses the provider message ID and source evidence to reconcile them. The input total includes ordinary input, cache reads, and cache creation. Claude's cache duration fields and Codex's cache duration fields have different meanings. Keep provider-specific values in the owning parser.

usage summarizes requests and prices them against dated provider tables. A measured zero, an unmeasured turn, and an unpriced request give different results. Preserve those distinctions through storage and rendering. A new rate needs an exact model match, applicable billing conditions, the source date, and tests at relevant thresholds. A supported correction uses the saved price snapshot and retains the previous evidence. Catalog changes must preserve the cost already recorded for an earlier request.

OpenAI requests above 272,000 input tokens use long-context rates for the full request. For GPT-6.2 Ultrafast, use the request timestamp to choose the rate before or after midnight Pacific time on March 1, 2027. An unavailable timestamp leaves that tier unpriced. See OpenAI API pricing.

For a calculation change, compare own-session and family totals. Then compare the mixed-agent project total, including archived and deleted chats. For a cache percentage, divide the summed cache reads by the summed inputs when both are known. For example, counts of 10/20 and 10/80 give a total of 20/100, or 20%. Averaging the two percentages would give 31.25%. A missing count requires an unknown indicator. The UI calls the recorded price the estimated API equivalent.

Set up signed releases

Add the following six values as repository secrets under Settings → Secrets and variables → Actions → Secrets → New repository secret. The workflow reads these secrets directly. Use an active Apple Developer Program membership for Developer ID signing and notarization.

  1. Open Keychain Access → Certificate Assistant → Request a Certificate From a Certificate Authority on your Mac. Save the certificate signing request to disk. Keep the private key on that Mac.
  2. Open Apple Developer → Certificates, Identifiers & Profiles → Certificates. Create a Developer ID Application certificate with that request. The Account Holder must create this certificate. Download the .cer file and open it on the same Mac.
  3. In Keychain Access → login → My Certificates, export the Developer ID Application certificate with its private key as a .p12 file. Choose an export password. Store this password as APPLE_CERTIFICATE_PASSWORD.
  4. Run the Base64 command below with your exported file. Store the copied text as APPLE_CERTIFICATE.
openssl base64 -A -in "/path/to/DeveloperID.p12" | pbcopy
  1. Run security find-identity -v -p codesigning. Store the complete name inside quotation marks as APPLE_SIGNING_IDENTITY, for example Developer ID Application: Example Company (TEAMID). Omit the quotation marks and certificate hash.
  2. Open App Store Connect → Users and Access → Integrations → App Store Connect API → Team Keys. Ask the Account Holder or an Admin to generate a Team API key with Developer access. Store its Key ID as APPLE_API_KEY.
  3. On the same page, copy the Issuer ID above the keys table. Store it as APPLE_API_ISSUER. This is different from the Apple Team ID.
  4. Download the API key's AuthKey_<KEY_ID>.p8 file. Apple permits one download. Store its complete text as APPLE_API_KEY_CONTENT, including the BEGIN PRIVATE KEY and END PRIVATE KEY lines. Preserve the line breaks. Use the raw text without Base64 conversion.
  5. Push a commit to trunk whose message contains new-release, for example new-release: publish Tugboat. With several commits in one push, the latest commit must contain the marker. Missing credentials or failed verification stop the release. GitHub supplies the publication token, and the release script creates the temporary keychain password and APPLE_API_KEY_PATH.

Resolve an invalid notarization key

The workflow checks APPLE_API_KEY_CONTENT before installing dependencies or preparing the native runtime. The release script repeats this check before accessing the keychain. The check accepts a complete raw PKCS#8 private key with the P-256 curve. It rejects Base64-wrapped files, literal \n text, incomplete files, and other key types without logging the key. This local check does not verify the key's Apple account, Key ID, permissions, or revocation status.

If notarization reports invalidP8, replace APPLE_API_KEY_CONTENT from the original AuthKey_<KEY_ID>.p8 file. With GitHub CLI installed and signed in, run the command below. It reads the file directly and preserves its line breaks.

gh secret set APPLE_API_KEY_CONTENT --repo reformo/tugboat < "/path/to/AuthKey_KEYID.p8"

Alternatively, run pbcopy < "/path/to/AuthKey_KEYID.p8" and paste into the repository secret's update form. Include both -----BEGIN PRIVATE KEY----- and -----END PRIVATE KEY-----. Confirm that APPLE_API_KEY matches the file's Key ID and that APPLE_API_ISSUER belongs to the same team. If the original file is unavailable, generate a replacement Team API key and update these three secrets together. Then rerun the failed release job.
