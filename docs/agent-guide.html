Agent guide

Use this guide when working on Tugboat itself. Before changing a command, identify where it will run, whose data it can reach, and which result would prove it worked.

Start a task

  1. Read the root AGENTS.md and this guide in full. Follow any more specific instructions for the files in scope.
  2. Check the current branch and working tree. Use git status --short --branch and inspect the diff for your target files. Treat existing changes as the user's work.
  3. Find the actual entry point and its test. Search the current checkout for the control label, command name, event, or schema field. Use implementation and tests to resolve differences with older plans.
  4. State the user-visible result and the check that will prove it. For a multi-step task, include a failure or cancellation case when it affects the change.

Carry out authorized local edits and isolated checks. Reuse a decision the user has already made for the same target and effects. Resolve routine choices from source and project conventions. Ask for a decision when an unresolved choice changes shared data, platform support, compatibility, or an external effect.

Select the correct owner

UI action or display
Trace the control in the root index.html through its TypeScript controller. Keep layout, focus, and temporary view state in the interface. A native command must still check the target when the user has switched projects since the action began.
Project or agent environment
Use the registry to resolve the project ID and environment ID. CPU, memory, and image verification are project resources. The network mode, policy, profile, guest home, and preparation attempt belong to an environment. Preserve the other agent's environment when changing one target.
Chat or terminal
Use the project, environment, and native session ID together to identify a chat. A terminal identifier selects a live process or retained view. Use the terminal registry to find a running chat. Reusing the last visible terminal can send an action to the wrong process.
Provider or usage record
Account renewals belong to the provider on the Mac. Usage belongs to the observed project, environment and session. Use the existing provider or storage API. Preserve the distinction between provider identity, transcript identity, and user-visible titles.

Preserve execution and account boundaries

Mac or guest. A local terminal executes on the Mac. Agent chats and guest Git or test actions run inside Brig. Use the existing typed operation, argument builder and checked plan for a new guest action. Pass variable arguments as values. Keep process timeouts, output limits, cancellation and exit status visible to the caller.

File access. The guest can write the selected local project. Check folder and volume identity before work that depends on that path. Validate the resolved guest home and project share. Keep the records folder, shared account files and unrelated host paths outside the plan's exposed directories.

Network and permissions. Follow the selected guest policy and the agent's supported permission mode. Codex uses Brig by default and also supports its optional workspace sandbox. Claude uses manual permissions. Probe results apply to the tested guest and plan. Keep an inconclusive result visible if the available evidence cannot distinguish a network failure from a policy denial.

Accounts. Keep renewable credentials in the native provider store. Give guests only the access copy supported by their profile. Preserve unrelated Claude connector credentials. A visible account field, diagnostic record, test fixture, or terminal error must not expose tokens. Exercise login with synthetic responses when checking cancel, retry or a late callback.

Cleanup. A policy document can be shared even when Tugboat owns a binding. For removal, use the preview, target fingerprint, ownership checks and saved checkpoints. If a file or environment has been replaced since the preview, preserve the replacement. Keep Forget, Stop, Remove and Sign out as distinct operations.

Protect saved records

For persistence changes, identify the writer, transaction, reader, previous format, and recovery path first. Use a temporary records directory with generated fixtures. Starting the desktop app runs normal storage activation and can import real records.

  • Use the verified records directory and its dataset ID. Respect its lock and directory marker. A missing drive or active database requires recovery. Creating an empty replacement can disconnect the user's history.
  • After activation, use usage_store for usage and saved chat state. Keep usage facts, parser progress and affected summaries consistent across a commit or retry. Retain immutable migration inputs and backups.
  • Read native transcripts from the verified guest home. Bound file traversal and parsing. Preserve project membership and parent evidence. Equal titles or token counts are insufficient to merge records.
  • Preserve measured zero, partial coverage, unknown counts and unpriced requests. Keep saved prices and correction evidence. A fresh catalogue is insufficient reason to reprice past requests.
  • Route record moves through the existing location transaction. Close writers, verify the destination, then commit the pointer. Leave journal recovery to SQLite. Test an interrupted move and a missing source using disposable data.

Add a feature

  1. Describe one observable outcome. For a guest Git action, specify the selected project, the selected agent, the command result, and where the user can read it.
  2. Trace one similar action end to end. Follow its control, controller, native command registration, domain operation and result. Reuse that path when its permissions and lifetime match the requested behavior.
  3. Define the affected transitions. List the initial state, the event, its preconditions, the success state and the failure state. Include cancel, retry, and late completion when the operation can outlive its view.
  4. Validate at the boundary. Check external arguments, paths, Brig responses and persisted input before mutating state. Preserve the wire names shared by Rust and TypeScript. Add a schema change only when the existing facts cannot represent the feature.
  5. Choose the smallest change. Extend the owning module, type or reducer. Keep public behavior and old records compatible where the user requested no change. Leave unrelated work in place.
  6. Test the behavior at the relevant layer. For the guest action, inspect the command target with a fixture. Exercise a changed plan and a project switch during launch. Confirm that a different environment's terminal keeps its state.
  7. Update the relevant guide. Change user steps when a control or its effects change. Update the developer route when ownership changes. Record a durable new architectural decision in the single ADR file using the next unused ID.

For a reproducible defect, first capture the failing behavior in a regression test. Confirm the fix through the normal entry point. A test for a new helper alone can miss the original failure.

Choose checks

Read a script before running it if the task restricts signing, network access, credentials, disk images, or live data. Match the check to the effect under review.

Interface or command arguments
Use node --experimental-vm-modules --test tests/frontend/*.test.mjs for the fixture interface. Use npm run build for TypeScript and the Vite build. A fixture can prove routing, selection and display. A native window, guest process or provider connection needs separate evidence.
Rust, terminal or guest adapter
Use the owning Rust tests with cargo test --manifest-path src-tauri/Cargo.toml --locked on the supported Mac with prepared dependencies. Choose the native terminal, hull, or Brig check for changes in that layer. Check the script's prerequisites and effects before choosing the preparation route.
Usage migration or storage recovery
Use the checked-in SQLite fixtures and the disposable acceptance tests. Include old data, two agent environments, duplicate replay and an interrupted transaction when those cases affect the change. For a performance claim, identify the fixture, baseline and measurement.
Restricted signing or release work
The full Node suite includes a macOS test that signs a temporary binary. Standard Tauri hooks also prepare native tools. The pull request workflow has a --no-sign preparation mode for explicit signing steps. Compilers can still add ad hoc signatures. Use the verification procedure that matches the actual restriction.
Local documentation
Open the HTML from the repository. Check filenames, fragment links, visible labels, table readability and keyboard navigation. For this handbook, verify the light palette on a dark-system preference as well.

Before a service-backed check, verify the account, guest, records directory and cleanup target. A local implementation request covers necessary isolated checks. Shared-data changes, deployment, or remote synchronization require authority for that effect.

Review and report the result

Read your final diff alongside the user's request. For each changed module, identify the public behavior and the owning test. Check that earlier changes in the worktree remain intact. For identity-sensitive operations, include an unaffected sibling project or environment in the review.

Report what the user can now do, the checks that ran, and any condition those checks did not exercise. Name the evidence when a claim depends on a real guest, a provider account, a database migration, performance, or package signing. Use the exact result of that check.
