Architecture decisions

The project folder belongs to the user. Brig runs the agents. Tugboat connects these systems and owns the records that let a user return to a chat.

This architecture decision record (ADR) covers the Tugboat 0.3.0 source reviewed on 14 November 2026. Each numbered decision describes behavior implemented in this checkout. A reason marked “inferred” explains the construction seen in code. A recorded reason comes from a project document, implementation comment, or test.

Desktop and runtime

ADR-001 · Use a Tauri window with a native command boundary

Vite builds the TypeScript interface for a Tauri 2 webview on Apple silicon Macs with macOS 15 or later. Rust registers named commands for project, account, storage, and terminal operations. Native events tell the interface when state changes.

Reason (inferred)
The interface can show the same project and session in several views. One native owner can verify a request against the current records and Brig state.
Consequence
A new command needs a Rust handler and matching frontend arguments. The main window restricts navigation and denies new webview windows. The configured capability grants event listening and removal of listeners. Provider sign-in opens the system browser.

Source files · Command registration and window navigation · Window and content security policy · Main window capability · Frontend state store

ADR-002 · Give each terminal a native surface and a process

Rust starts the process on a pseudo-terminal (PTY). An AppKit view uses libghostty-vt for terminal emulation. The webview requests placement, focus, visibility, and closure by terminal ID. Switching chats brings the selected surface back with its scrollback.

Recorded reason
Chats need interactive text input, approval prompts, keyboard signals, and the ability to continue while the user views another chat.
Consequence
Process exit and surface disposal are separate events. Diagnostic output can remain visible after the process exits. The app limits live processes to 16 and retained finished views to 32. Terminal changes can affect the PTY, the native view on the main thread, and the TypeScript layout controller.

Source files · Product behavior · Terminal registry and limits · PTY lifecycle · AppKit surface · Layout queue

ADR-003 · Ship a pinned Brig runtime with the app

An empty Brig path selects the bundled executable. Tugboat includes Brig, hull, the virtual machine runners, cosign, and the required ext4 disk tools. Build scripts check pinned inputs. A manifest records the packaged files and their hashes. The Mac check validates the runtime and checks the Brig version.

Recorded reason
The packaged runtime can prepare public guest images on a Mac without Homebrew. Patches make the disk tools available inside the app and support shared folder paths that contain spaces.
Consequence
A saved absolute path can select a compatible Brig executable. An invalid override gives an error. A release still needs the other bundled tools. The first guest start can need internet access for images and boot assets. The bundled registry configuration keeps public image pulls separate from the host Docker credential store.

Source files · Runtime requirements · Release input pins · Runtime assembly · Manifest verification · CLI selection and checks · Registry configuration

Projects and environments

ADR-004 · Register a folder once and identify each agent environment separately

A project record keeps a stable ID and folder identity. The registry checks the volume, inode, and creation time when matching a folder. It derives an environment ID from the project ID and agent kind. A project supports one Codex environment and one Claude Code environment.

Recorded reason
The user can work on the same folder with either agent. Each agent needs its own guest home, policy, lifecycle, and chat history. Disk remounts must preserve the connection to the original project.
Consequence
CPU count, memory, and image verification are project settings. Network mode, policy, and preparation state belong to each environment. Changing shared resources invalidates preparation for the other environment. A different folder at the saved path fails the identity check. Two agents can use the same native chat ID in distinct environments.

Source files · Project requirements · Folder identity and registry · Shared resources · Environment ownership · Environment identity

ADR-005 · Verify the Brig execution plan before starting work

Rust resolves the saved project and environment. It compares the current Brig policy to the saved fingerprint, a hash of its contents. It validates the execution plan and derives a second fingerprint from the project, environment, agent kind, profile, and executable plan fields.

Reason (inferred)
A policy, folder, or running guest can change after the interface shows a preview. A process launched from an old preview could act on a different target.
Consequence
A valid plan identifies the expected writable project share, hull/hvi runtime, profile, session, network mode, resource limits, and image verification setting. It must satisfy the checks on credentials, host skills, published ports, and private record paths. A changed fingerprint requires a new preview. Guest operations use the verified environment. Open local terminal explicitly starts a Mac shell in the host project folder.

Source files · Checked environment and plan fingerprint · Brig plan validation · Session launch checks · Local shell command

ADR-006 · Apply the network policy to a specific Brig environment

New settings use isolated networking and agent-specific host lists. The user can select offline mode. The app requires a bound policy that denies other outbound traffic by default. Changing application defaults affects new policies. Editing an existing policy requires the stopped environment and the current policy fingerprint.

Recorded reason
Different agents need different service hosts. The project owner can review the actual policy and its binding independently of the application defaults.
Consequence
The editor limits changes to supported, owned policy documents and bindings. Guest host rules apply to resolved addresses. Two services can share an address, so a boundary test can report an inconclusive result. Provider sign-in on the Mac and provider-hosted tools have separate network paths.

Source files · Network behavior · Agent defaults · Policy edits · Ownership rules · Boundary checks

ADR-007 · Keep agent permission modes in each agent adapter

Both agents run inside Brig. New and resumed Codex chats default to --sandbox danger-full-access --ask-for-approval never. The alternative uses workspace-write with command network access disabled and the same approval setting. Claude Code uses --permission-mode manual.

Recorded reason
Brig supplies the outer file and network boundary. Codex supports a second workspace restriction. Claude supplies its own interactive permission flow.
Consequence
The default permits Codex to act throughout its guest and to write the shared host project folder. Claude can ask the user to approve or deny an action. The launch path checks the supported capabilities of the selected guest program. Boundary checks report observations independently of the selected permission mode.

Source files · Guest access settings · Codex arguments · Claude arguments · Claude capability check · Agent boundary contract

ADR-008 · Retain ownership and progress through environment removal

Preparation can adopt a matching Brig session. Multiple matches require an explicit choice. The app records ownership of the session, binding, and policy separately. Removal takes a preview for one environment or for all environments in the project. It checks the fingerprint and the typed confirmation against the current target.

Reason (inferred)
A user can manage Brig outside Tugboat. A removal request spans several external operations. An interruption can leave some steps complete.
Consequence
Removal saves its progress through optional guest sign-out, environment removal, binding cleanup, policy cleanup, and record removal. A retry checks the live target again. Shared or externally changed policies survive cleanup. Forget removes the project registration and retains its project files, guest resources, and saved usage. A confirmed environment removal can remove its guest home.

Source files · Adoption choices · Preview scope · Removal checkpoints · Cleanup and recovery · Forget operation

Provider accounts

ADR-009 · Keep one renewable host account per provider

Tugboat stores renewable credentials in private files under the active records folder. ChatGPT uses chatgpt/session.json. Claude uses claude/session.json. Each eligible environment receives access credentials for its own provider. The host retains the refresh token.

Recorded reason
The user can sign in once across projects while each environment keeps its own configuration, policy, history, and lifecycle.
Consequence
Shared Codex sign-in requires the standard guest credential directory. New chats disable the shared Codex daemon to avoid retaining earlier credentials. Managed Claude guests receive an access copy in memory through the guest helper. The helper preserves independent connector records. Project removal preserves the host accounts. Shared sign-out checks active sessions for the affected provider.

Source files · Shared account behavior · Codex guest eligibility · Codex access copy · Claude memory and persistent mounts · Claude guest update

ADR-010 · Run browser authorization from the Mac

The account command starts a native sign-in attempt for the selected provider. ChatGPT uses device authorization. Claude uses Proof Key for Code Exchange (PKCE) and a temporary loopback callback. Rust opens the provider page, verifies the response, exchanges credentials, and saves the account.

Recorded reason
Settings must let a user connect before adding a project or starting a guest. The authorization attempt has its own lifetime, including cancellation.
Consequence
The webview receives the phase, browser address, optional device code, and message. Rust owns secret protocol values and checks the attempt ID before accepting a late result. The user can cancel until saving begins. A connected guest still uses its environment policy for model requests.

Source files · Provider settings · Provider protocols · Loopback callback · Attempt state and public status · Attempt ownership checks

Conversations and usage

ADR-011 · Resume from agent transcripts and group verified descendants under the root chat

Codex owns its rollout files. Claude owns its persistent transcripts. Readers associate the native session and working directory with the verified environment. A conversation graph links a subagent to its parent when the records support that link. Normal forks remain separate chats.

Recorded reason
The session list must show each root once and include its nested agents. A title or a shared project path alone cannot establish a parent.
Consequence
A root can resume when the required source and environment checks pass. Claude new chats receive an app-generated session ID. Codex generates its own ID. An unresolved child goes to read-only recovery. Archive and Trash change the root's saved state. They preserve native transcripts, child records, and project usage.

Source files · Root and subagent behavior · Relationship checks · Claude parent evidence · Claude resume check · Saved state and details

ADR-012 · Count recorded work by source identity and carry missing data into totals

For a Codex request with source evidence, the identity includes the verified guest namespace, provider, origin thread ID, and response ID. Claude merges repeated message observations using stable identifiers. Family totals include verified descendants. Saved evidence distinguishes unknown consumption from a measured zero.

Recorded reason
Forks can copy past Codex events. A Claude transcript can contain several observations of one response. An incomplete transcript can omit a request or a child.
Consequence
Equal token counts or equal native session IDs in separate environments cannot establish duplicate work. Saved usage can remain available after a transcript disappears. Claude coverage remains partial and the reader cannot attribute its usage to individual user prompts. A source coverage label describes the available local evidence.

Source files · Usage contract · Physical request key and totals · Copied Codex history · Claude measurement and merge · Family details

ADR-013 · Save dated rates, assumptions, and corrections with each priced request

The usage layer calculates a token cost estimate from recorded counts and the applicable provider rates. It keeps the date, rates, and pricing evidence with the request. Different cache lifetimes, service tiers, and provider rules can produce different estimates.

Recorded reason
The user needs a reproducible estimate even after a catalogue update or loss of the source transcript. The evidence must show which rates were known and which values the calculation assumed.
Consequence
New catalogue rates apply when pricing eligible requests. Historical repricing and count corrections require evidence. Saved Claude counts can receive prices offline. Invalid pricing inputs stay unpriced. Project totals can contain a known subtotal and additional unpriced work. The estimate excludes subscription charges, account discounts, tool charges, and taxes.

Source files · Cost estimate scope · Rate snapshots and corrections · Claude tariffs · Price evidence · Offline pricing transaction

Records and recovery

ADR-014 · Store usage facts for both agents in one database per records folder

The active usage.sqlite3 holds environment keys, session records, turns, requests, historical corrections, and parser positions. It stores per-session summaries for dashboard reads. Configuration, account records, profiles, location metadata, and native transcripts retain their own formats and owners.

Recorded reason
Adding one request or changing one chat state used to require a whole ledger rewrite. Session and request rows allow smaller reads and writes. One transaction can commit both a measurement and the parser position that produced it.
Consequence
Runtime access uses a shared database handle. The store checks the dataset identity and its file binding. It enables foreign keys, a rollback journal, and extra synchronization. Each durable write has a synchronization cost, even for a small append. If a commit result is uncertain, the next access must verify the database before processing resumes.

Source files · Database schema · Shared database handle · Identity and recovery checks · Transactions · Scoped scanning

ADR-015 · Activate the SQLite writer only after verifying the legacy import

SQLite schema 1, legacy JSON ledger schemas 1 and 2, and the records directory marker have separate version numbers. On migration, Tugboat inventories sources, retains required immutable backups, and imports into a private staging database. It checks parity and source hashes, publishes the database, then advances the directory marker to version 2.

Reason (inferred)
Restarting between publication steps must preserve a recoverable dataset. Enabling the new writer before validation could accept incomplete facts or lose a later update.
Consequence
After activation, SQLite owns new writes. Original JSON files can be older than the database. An absent, damaged, or mismatched active database blocks usage access. Recovery requires the verified active dataset or a matching SQLite backup. A marker change or a legacy ledger alone cannot recover later SQL writes.

Source files · Activation order · Input inventory and backups · Interrupted imports · SQLite version · Directory marker

ADR-016 · Move records as a verified dataset on restart

Tugboat resolves the active records folder before opening usage storage. The default folder under ~/Library/Application Support/Tugboat holds the location pointer and its lock. A move records the intended destination first. On restart it copies the closed dataset, verifies it, marks the target complete, commits the pointer, and cleans the old location.

Recorded reason
A removable disk can disappear at any stage. Settings, project identities, provider accounts, usage, and backups must continue to refer to the same dataset.
Consequence
An incomplete target cannot become active. A missing disk leaves recovery available. Locate checks the dataset ID. SQLite checks include integrity, foreign keys, and matching copy hashes. Private records must stay outside project shares and guest homes. Moving records leaves Brig guest homes and their transcripts in place.

Source files · Records location contract · Move and locate transactions · Move states · Closed database verification · Record publication

ADR-017 · Give asynchronous workflows explicit states and a defined owner

Native code owns environment operations, sign-in attempts, storage state, and shutdown. The interface tracks which request and project own a pending screen update. For example, a dashboard reply can arrive after the user has selected another project. The request revision lets the controller reject that reply.

Recorded reason
A workflow can fail, finish late, or receive a second request while work is still pending. Its current state determines which transition can succeed.
Consequence
Shutdown requests confirmation when a process is running. After approval, the app drains processes, waits for account writes, records final usage, and closes storage before exit or restart. A failed final scan or database close interrupts shutdown. Implementations must handle the partial effects, including a process that already exited.

Source files · Repository workflow rules · Dashboard updates · Request revisions · Environment operation ownership · Shutdown ordering · Exit permission

Build and distribution

ADR-018 · Separate pull request checks, installer publication, and Apple distribution verification

Pull request jobs have read-only repository permissions. They run the web checks on Linux. Changes to native dependencies or source trigger macOS checks. A separate workflow for pushes to trunk builds the Apple silicon disk image (DMG), checks the packaged runtime, and publishes it with a build-specific tag.

Reason (inferred)
Frontend tests can run without a Mac. Native terminal, filesystem, virtual machine, and packaging behavior need macOS tools. Publishing an installer requires separate write access.
Consequence
The current trunk workflow builds with an ad hoc signing identity. Its package checks establish the version, disk image, and bundled runtime. Developer ID distribution uses the separate signing and notarization script. The release verifier checks Apple tickets and Gatekeeper on a mounted installer. Upstream runner signatures have their own verification step.

Source files · Pull request checks · Trunk publication · Bundle settings · Developer ID release script · Apple distribution checks · Runner checks
